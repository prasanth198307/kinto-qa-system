KINTO Operations
Multi-Tenant Architecture

Detailed Implementation Plan

Version: 1.0 | Date: December 14, 2025

Executive Summary

This document outlines the complete implementation plan for transforming KINTO Operations from a single-tenant application to a full-featured multi-tenant SaaS platform using PostgreSQL's schema-per-tenant approach.

Key Benefits

  • Complete data isolation between tenants
  • Per-tenant backup and restore capabilities
  • Configurable features and modules per organization
  • Customizable screen layouts and fields
  • Flexible licensing and user management
  • Scalable architecture for growth

2.2 Tenant Schema Tables

Each tenant schema (org_kinto, org_acme) contains identical copies of all operational tables:

  • Core: machines, products, raw_materials, inventory
  • Checklist: checklist_templates, assignments, submissions
  • Sales: vendors, invoices, gatepasses, credit_notes
  • Production: production_entries, bom_configurations
  • Maintenance: maintenance_plans, pm_executions

7. WhatsApp Integration for Multi-Tenant

Routing Flow

WhatsApp Message Received ↓ Webhook: /api/whatsapp/webhook (single endpoint) ↓ Look up user by phone number (public.users) ↓ Get user's organizationId ↓ SET search_path TO org_{slug} ↓ Process in tenant context
Important: Phone numbers must be unique across the entire platform. One phone = One user = One organization. This ensures clean routing without ambiguity.

8. Migration Strategy

Migration Steps

  1. Add New Tables (No Downtime) - Create organizations, plans tables
  2. Create First Tenant (5 min downtime) - Move existing tables to org_kinto schema
  3. Enable Multi-Tenant Mode - Flip feature flag to true

Rollback Plan

If issues occur, tables can be moved back to public schema and feature flag disabled.
