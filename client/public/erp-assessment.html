How Navigation Filtering Works

The hook usePlanFeatures fetches the tenant's allowedNavItems from the server. The use-filtered-navigation.tsx hook (477 lines) filters the sidebar navigation against this list — so a Basic plan tenant never sees the Accounting or HR modules in the menu. Backend plan-middleware enforces the same at the API level, returning 403 for out-of-plan routes.

How to Add a New Shared Module

  1. Add the module key to server/plan-features.ts → MODULE_NAV_ITEMS
  2. Add screen keys to shared/screen-registry.ts
  3. Add nav path → screen key mapping in shared/nav-screen-map.ts
  4. Build the API routes (any prefix) and mount in server/routes.ts
  5. Build the UI pages in client/src/pages/
  6. Add route to client/src/App.tsx
  7. Server auto-patches screen permissions to all admin roles on next restart

How Enforcement Works

Step 1 — Plan check at login: Session stores tenantPlan and allowedModules.

Step 2 — Backend enforcement: plan-middleware.ts checks every request's route prefix against ROUTE_PLAN_REQUIREMENTS. If the tenant's plan doesn't include the module → 403 Forbidden.

Step 3 — Frontend enforcement: usePlanFeatures hook filters the sidebar navigation. Modules not in the plan are hidden from the UI.

Step 4 — Module Marketplace: Tenants can purchase individual modules without upgrading their base plan via the subscriptions.selected_modules table.

Trial bypass: Trial tenants bypass all plan checks — they see and access everything.

⚠️ Gap: 8 Verticals Have No Subscription Plans

NGO, Nidhi Company, CRM, Logistics, Real Estate, Agriculture, Education, E-Commerce have no vertical-specific subscription plans. They are only accessible via generic enterprise or trial. Need Starter/Professional/Enterprise tiers for each.

What Gets Loaded for Each Plan

When a tenant with plan professional logs in:

  • Sidebar shows only: Invoicing, Purchase Orders, Inventory, Production, Accounting, MIS, Warehouses, Expenses — no HR, no verticals
  • API calls to /api/hr return 403
  • Screen permission checks pass only for screens in allowed modules
  • The same React app bundle is served — no separate JS bundle per plan. Plan filtering is runtime logic, not build-time code splitting

Dynamic Roles & Users Per Plan — How It Works

How Roles Are Enforced

Auth: Passport.js local strategy. Session stores tenantId, tenantPlan, role. Super-admins can impersonate tenants with session-swap (logged).

RBAC Schema: role_permissions table: { roleId, screenKey, canView, canCreate, canEdit, canDelete, tenantId } — screen-level CRUD control with 110+ screen keys.

Two-layer gate:

  1. Plan gate first — route prefix checked against tenant's plan modules → 403 if not in plan
  2. RBAC gate second — role_permissions checked for the specific screenKey + HTTP method → 403 if no permission

Tenant isolation: Every DB query scoped by tenant_id from session. One tenant's roles and data never affect another.

Tenant admins CAN: Create custom roles, assign any combination of 110+ screen keys with granular CRUD permissions per screen.

What Works ✅

  • Custom roles with screen-level CRUD (view/create/edit/delete per screen)
  • 110+ screen keys covering all shared modules + all vertical sub-pages
  • Plan-boundary respected — role permissions only matter within the plan's allowed modules
  • Tenant admin can create unlimited custom roles
  • Super-admin can impersonate any tenant
  • Auto-patching: new screens added to nav-screen-map.ts are auto-granted to admin roles on server restart
