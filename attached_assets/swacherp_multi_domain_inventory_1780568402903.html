Architecture answer — one engine, domain profiles
Single inventory engine with domain-specific field profiles
Shared core
Item master (name, barcode/SKU, category, UOM, HSN, GST%), stock levels per warehouse, GRN, stock transfers, bulk upload, barcode scan — identical across all domains. Built once.
Domain profile
Extra fields and rules activated per tenant's domain setting. Grocery activates MRP lock + expiry + weighing scale. Pharmacy activates Schedule H + batch mandatory. Restaurant activates recipe/BOM. Apparel activates size-colour matrix.
POS linkage
Only domains with a retail counter (Grocery, Pharmacy, Apparel) connect inventory to POS terminal. Restaurant connects to Kitchen Display System (KDS) + recipe consumption instead. Services skip POS entirely.

Bulk upload — what changes per domain
Grocery template columns
Barcode, name, category, HSN, GST%, MRP, purchase rate, selling price, UOM, expiry tracking Y/N, reorder level, warehouse
Pharmacy template columns
Same as grocery + Drug schedule (H/H1/OTC), composition, manufacturer, pack size, mandatory batch required Y/N, controlled substance Y/N
Restaurant template columns
Ingredient name, category, UOM (kg/ltr/pcs), purchase rate, par level, supplier code — NO barcode/MRP/GST (ingredients aren't sold directly)
Apparel template columns
Style code, product name, category, colour, size, MRP, selling price, HSN, GST% — one row per size-colour combination, not per product
Implementation: one base template with domain-specific extra columns appended. The upload engine reads the domain profile and validates accordingly. A grocery upload with "Drug schedule" column is ignored. A pharmacy upload missing "Pack size" throws a validation error.
